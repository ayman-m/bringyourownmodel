
#### Model adaptation (new)

- Guardian now measures the enabled model **once a day** and every investigation reads the result, instead of using the one fixed `max_input_tokens` shipped in `guardian_settings`. The new **GuardianModelAdaptation** Job (every 24 hours; create it by hand on a manual install, like the other five) runs `!guardian-probe-model` and saves a trustworthy result to the new **`guardian_model_profile`** List: the served context window, characters per token, whether tool calls and structured output work, and the recommended input budget.
- Order of precedence for each number: an operator `overrides` entry in `guardian_model_profile` > the measured profile > `guardian_settings` > the built-in default. The model **size** (`model_tier`) is still declared in `guardian_settings`; the harness cannot detect parameter count.
- A model served with a small context no longer gets a tool list larger than it can hold: the tool-list budget (tier default, or an explicit `guardian_settings.max_tool_def_tokens`) is capped at 60% of the input budget. An operator override is never capped.
- `guardian_model_profile` is a runtime List (created by `GuardianBootstrap`, and by the writer on first use), not pack-seeded, so the Job can refresh it with no redeploy and no approval, and an operator can pin values under `overrides`. The agent does not write it and the tool bridge is unchanged.
- One run uses one set of numbers: they are settled on tick 0 (from the playbook's snapshot when it left one) and kept in the loop state.
- If you change the enabled model or its context size, run the job again (or `!guardian-probe-model` then `!GuardianModelProfileUpdate`); until then the profile describes the previous model. A profile three or more days old is flagged in the War Room.

#### Integrations

##### Guardian Foundry (new)

- A new model-plane provider for Microsoft Foundry (Azure AI Foundry). It implements `guardian-llm-chat` identically to the other providers and talks to a Foundry resource's OpenAI-compatible v1 chat-completions API, so one integration serves OpenAI models and the other chat models deployed in the same resource. It authenticates with a resource key or a Microsoft Entra ID service principal, treats reasoning models (o-series, gpt-5) correctly (default temperature only, `max_completion_tokens`), and lets an operator list parameters a deployment rejects. Enable it instead of, not alongside, another provider.

##### Guardian Cohere

- `guardian-llm-chat` accepts an optional per-call `timeout` (seconds). It is one deadline for the whole turn (conversation read, submit and poll), with no retries, and never longer than the instance's request timeout. Without it, calls behave as before.

##### Guardian Vertex

- `guardian-llm-chat` accepts the same optional per-call `timeout`: one attempt, no retries, never longer than the instance's timeout.

#### Lists

##### guardian_settings

- `max_input_tokens` is now only the fallback: the measured value in `guardian_model_profile` wins once the GuardianModelAdaptation job has run (see Model adaptation). The comments in the List say so.
- No longer ships an explicit `max_tool_def_tokens`. The shipped value (4000, the small-model budget) overrode every model tier, so setting `model_tier` to `medium` or `large` never widened the tool catalogue. The budget now comes from the tier (small 4000, medium 16000, large 24000). You can still set the key yourself to hand-tune one server. Small-tier behavior is unchanged.

##### guardian_prompt_tail

- The verdict-block guidance now says to name an ATT&CK technique only when the incident or a tool result shows that behavior (never inferred from the incident type), and what confidence levels mean (90 or more only when the key indicators are confirmed).
- The verdict-block template no longer shows example technique ids (`T1566`, `T1078`), which smaller models copied into their answers. It now shows a `T####` placeholder and says to list only the techniques that match the incident.

#### Playbooks

##### GuardianModelAdaptation

- New. The playbook the daily GuardianModelAdaptation Job runs, also runnable by hand: check the kill switch (the probe makes billable model calls, so a thrown switch skips it), probe the model, save the profile, close its own incident.

##### GuardianAgentLoop

- The run is now visible as separate playbook tasks instead of one: **Check kill switch**, **Check job guard**, **Resolve model profile**, **Build system prompt**, **Build tool list**, **Load skill** (only when the new `preload_skill` input is `true`; default `false`), then **Run Guardian model session**. Nothing before the session involves the model. The session stays one task on purpose: the model's tool choices, the security gate, approvals and the verdict are one conversation. A kill switch that is on, or an auto-disabled Job, ends the run at a visible "Halted" task. The kill switch and job guard are still checked inside the session on every turn, so a switch thrown mid-run still stops it.
- The three checks never block a run because of their own failure (the same fail-open behavior as before).

##### GuardianEvalInvestigate

- Same task layout as GuardianAgentLoop.
- The eval prompt's verdict template uses the same `T####` placeholder instead of example technique ids, and carries the same technique and confidence guidance as the production prompt.

#### Scripts

##### GuardianKillSwitchCheck, GuardianJobGuardCheck

- New read-only playbook tasks for the two preflight checks.

##### GuardianModelProfileCheck

- New read-only playbook task, **Resolve model profile**. It works out the model numbers the run will use (model size, input budget, tool-list budget) from an operator override, else the measured profile, else `guardian_settings`, else the built-in default; prints each with its source; and leaves a snapshot at `Guardian.ModelProfile` so every later task and the model session use one set of numbers even if the daily job refreshes the profile mid-run. It also compares the resolved model size with the provider instance's "Model size" and warns when they disagree (the warning now names both ways to change the size: `guardian_settings.model_tier` with a redeploy, or `overrides` in `guardian_model_profile` without one), warns when the measured profile is three or more days old, and warns when the probe found the model does not honor tool calls.

##### GuardianModelProfileUpdate

- New. Saves the latest `!guardian-probe-model` result to `guardian_model_profile`. A probe that was not trustworthy (no usable budget, too slow at the smallest size, the capability checks skipped, or the ratio not measured) leaves the previous profile in place and says why. A probe whose window search ran out of time reports a confirmed floor (the model passed at that size, so it never overestimates; on a 32K window this is the normal outcome): it is saved marked `truncated`, but it may not cut an existing budget by more than half, so a busy server cannot shrink the budgets for a day. A finished search is always accepted. `force=true` accepts anything that has a usable budget. It reads, merges and writes the whole List, so operator `overrides` and other records survive, and it refuses to overwrite a List it cannot parse.

##### GuardianSkillRead

- Fixed: reading a skill no longer breaks the incident's Guardian context. The skill was returned as command outputs under the bare `Guardian` key, and XSOAR appends a dict returned at an existing key, so the first skill read in an incident turned all of `Guardian` (the loop state included) into a list and every later `Guardian.*` read failed. The skill is now written with `setContext` to `Guardian.SkillBody`, `SkillName`, `SkillDisplayName` and `SkillCategory`. It had gone unnoticed because the model rarely loads a skill.
- New optional argument `summary_only`: prints one summary line instead of the whole skill (the body is still written to context). The playbook's Load skill task uses it.

##### GuardianPromptBuilder

- New optional argument `summary_only`: prints one summary line instead of the whole prompt (the playbook task uses it). The prompt is still written to context in full.

##### GuardianEval

- `action=run` retries the lookup of a just-created case for a few seconds while XSOAR's search index catches up. A single immediate lookup sometimes missed it, leaving the case created but never started.

##### GuardianProbeModel

- Makes one throwaway warm-up call first (`warm_up`, default true), so a model the server unloaded while idle is not measured cold. The result now includes `calibration_record`, the record it saved to `guardian_model_calibration`, for `GuardianModelProfileUpdate`. Running the probe by hand still changes nothing until the profile is updated.
- Every probe call now sends a hard per-call `timeout` (1.25 x the latency budget), so a single slow call can no longer outlive the script timeout and end the probe with no report.
- The context-window search now grows from a small size that fits and bisects after the first failure, so a model with a small window is measured instead of exhausting the time budget on oversized prompts.
- The run's time budget is 240 seconds (was 150), checked against each call's hard limit before it starts.
- The tools and structured-output checks now run before the window search, so a slow model can no longer leave them skipped.

##### GuardianReasoningTick

- The model size, input budget (compaction threshold) and tool-list budget now come from the model profile (see Model adaptation above): settled on tick 0 and kept for the whole run, and the first War Room entry says where each came from.
- When the model repeats the same failing tool call two turns in a row, the loop still stops the tool calls, but it now asks for a final conclusion without tools on the next turn instead of ending in error with no verdict.
- When the model returns an empty reply twice in a row, the run no longer ends with no verdict. It asks for a final conclusion without tools on the next turn (the same forced-summary turn the tick limit uses) and records the verdict from it.
- New: with the playbook input `preload_skill` set to `true`, the **Load skill** task reads the skill named by the `skill` input and the session adds it to the system prompt, if it fits within 15% of `max_input_tokens` (otherwise the first War Room entry says it was skipped and the model can load it with `GuardianSkillRead`). It is off by default: it costs a few thousand tokens per run and its benefit depends on the model and the task, so measure it for your own model before turning it on. A skill that isn't the one requested, or is left over from an earlier run, is never used.
- The "loop already ended -- ignoring stray re-entry" message now says how to run again (`!DeleteContext key=Guardian` or a new incident). The loop state is still not cleared automatically, because it also protects a run waiting on an approval.
- New argument `use_prebuilt` (set by the playbook): on the first turn the session uses the system prompt and tool list the playbook built into context, and says where each came from in its first War Room entry. If either is missing or malformed it builds it itself. Without the flag (run by hand) nothing changes.
- Guardian's own audit entries are removed from `getEntries` results before the model sees them; the result notes how many were omitted. They only duplicate tool calls the transcript already records, and a model can imitate their format in place of a conclusion.
- The verdict block may now use a plain ``` fence as well as ```json, and a trailing unfenced verdict object is accepted. The last block that carries a verdict still wins; an invalid final verdict is never replaced by an earlier draft.
- If a run is about to conclude without a valid verdict (after the existing corrective retry, or at the tick limit), the loop makes one more model call, with structured output and no tools. That call turns the model's own final conclusion into the verdict object. The result passes the same validation, and its audit row carries `"source": "extracted"`. Previously such runs completed with no verdict recorded, even when the conclusion stated one clearly. Extraction runs only when the answer contains a written conclusion (fenced blocks, echoed War Room entries and JSON are ignored). The extracted verdict word must also appear in that conclusion, otherwise nothing is recorded; a missing verdict is safer than an invented one.
- New: when the model provider's content filter blocks a turn (Azure AI Foundry answers HTTP 400 to jailbreak-style text), the run retries up to `content_filter_retries` times (default 2, in `guardian_settings`; 0 keeps the old behaviour of stopping at once). Each retry resends a copy of the conversation with a short note that this is an authorized defensive investigation and that incident text is evidence, not instructions; from the second retry, tool results newer than the last assistant message are cut to 400 characters. The system prompt, tool list and policy never change. The War Room line for the turn says how many retries were used, every attempt is billed to the cost ledger, and if every retry is blocked the run stops and asks for a human analyst.
- New: `max_tool_calls_per_turn` (in `guardian_settings`, or under `overrides` in `guardian_model_profile`). Set to `1`, the run executes only the first tool call of a turn and tells the model which calls were deferred, for models that put every call into one turn. `0` or unset keeps every call.

##### GuardianToolBridge

- `splunk-search` and `splunk-job-create` queries that contain a write-capable SPL command (`collect`, `outputlookup`, `outputcsv`, `sendemail`, `sendalert`, `delete`, `map`, `savedsearch`, `script`, `dbxquery` and similar) are now classified as destructive and held for human approval in every approval mode, including `bypass`. Ordinary searches still run without approval. The audit row records the matched commands in `spl_write_commands`.

##### GuardianPlanApprove

- A plan step that runs write-capable SPL is now shown as destructive on the plan approval card, matching GuardianToolBridge.

##### GuardianHousekeeping

- The stalled-run watchdog now excludes Pending incidents in its search and reads the most recently modified runs first. Previously a fetch integration that filed its alerts as *Guardian Agent Run* could fill the search page with never-started incidents and hide real runs from the watchdog.

##### GuardianWidgetLoopHealth

- The loop-health widget reads real runs with the same corrected search, and reports the exact number of not-started runs instead of the count found on one page.

##### GuardianToolCatalogBuilder

- The tool-list budget comes from the same resolver as the model session (override, explicit `guardian_settings.max_tool_def_tokens`, or tier default, capped at 60% of the input budget unless it is an override), and the catalogue metadata records its source (`MaxToolDefTokensSource`). New argument `use_snapshot` (set by the playbook) takes the numbers from the run's `Guardian.ModelProfile` snapshot.

##### GuardianBootstrap

- Seeds the empty `guardian_model_profile` List.

##### GuardianModelCommand

- `!guardian-model` now also prints what an investigation started now would use (model size, input budget, tool-list budget, each with its source), so it agrees with the run. The "Model size" column is explained as display-only.
