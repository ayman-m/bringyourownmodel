# Guardian for the Cortex platform: differences from the XSOAR 6 pack

`Packs/GuardianXSIAM` started as a copy of `Packs/Guardian` (1.0.1 plus the model-profile work) and is maintained as a
second version. Fixes that are not platform-specific should be carried across by hand. Everything below is deliberate.

| Area | XSOAR 6 pack | Cortex platform pack | Why |
|---|---|---|---|
| Marketplace | `xsoar` | `marketplacev2` (every item yml/json and `pack_metadata.json`) | `-x` drops anything else |
| Shared code | `inject_common.py` block from `Packs/Guardian/Scripts/GuardianCommon` | the same script, run per pack, from `Packs/GuardianXSIAM/Scripts/GuardianCommon` | the two blocks may differ |
| Playbooks | no flag | every playbook carries `adopted: true`; after a pack install they must be adopted (`tools/adopt_playbooks.py` in the download, or re-save each playbook) | an unadopted playbook cannot be attached to an issue or run by a Job ("playbook is not adopted") |
| JSON command arguments | plain JSON text | `messages`, `tools`, `response_format` and the compaction transcript are sent as `b64:<base64 JSON>` (`guardian_arg_encode` / `guardian_arg_decode`); GuardianCohere, GuardianVertex, GuardianFoundry and GuardianCompact accept both forms | Cortex platform damages a JSON string argument that carries deeply nested backslash escapes (a stringified REST response in a tool result made a 58 KB `messages` invalid) |
| Pre-process rule | `GuardianIntakeHygiene` | removed | pre-process rules never fire on Cortex platform |
| Jobs | `type` is an incident type | `type` is `##default##`; a Job run is a `job-<id>` investigation with no issue attached | how Cortex platform runs Jobs |
| Stalled-run watchdog | finds stalled `Guardian Agent Run` incidents | only sees runs that have an issue (a Job run has none) | consequence of the row above |
| Tool risk tier | `xdr-*` containment names | adds every Cortex `core-*` / `xdr-*` command that is not a read; endpoint tag commands stay soft (pre-approved autonomy is unchanged) | Cortex platform ships its own response commands |
| Policy list | `xdr-*` / ews / splunk writes | adds the same `core-*` / `xdr-*` writes as `require_approval` | defense in depth; the allowlist is still default-deny |
| Tool allowlist | read tools | Cortex reads first (`core-get-issues`, `core-get-issue-recommendations`, `core-get-asset-details`, `core-get-case-extra-data`, `core-get-cases`, `GuardianXQL`, `xdr-xql-generic-query`, `xdr-xql-get-query-results`, vulnerabilities, assets, prevalence, risky users and hosts, ASM exposure); the XSOAR reads (`getIncidents`, `SearchIncidentsV2`, `getEntries`, `findIndicators`, Splunk, EWS) kept at the tail | the order is the priority when tool definitions must fit a small budget |
| Skills, prompt head and tail, persona | XSOAR incident workflow (`getIncidents`, `setIncident`, War Room, linked incidents) | written for issues and cases: an issue router picks one of six family skills (detection, misconfiguration, identity, vulnerable package, attack path, general), each ending in a report format and a conclusion block; `cortex_case_triage` and `cortex_platform_reference` are replaced by `cortex_issue_reference` | the platform has different commands, a different data model and mostly posture findings, not threats |
| Issue routing | `GuardianIncidentRoute` + list `guardian_incident_routes` (incident type, category, source brand, name and labels -> family, domain, skill, evidence plan); Guardian's own and simulation incidents get a note and no model run | `GuardianIssueRoute` + list `guardian_issue_routes` (domain, category, scanner, tags -> family, skill, evidence plan, assessment mode); health issues get a note and no model run | one generic task for every issue gave a threat verdict on a configuration finding |
| Deterministic triage | the same triage mode of `GuardianReasoningTick`, `GuardianTriageResult` and operator-owned `GuardianTriageApply` (severity and phase through `setIncident`, same guards), list `guardian_triage_types` with six XSOAR types (phishing, identity, endpoint, network, data exposure, vulnerability) plus `other`, skill `xsoar_triage`; both scripts denylisted. No posture mode: every focused session ends with a verdict | `GuardianReasoningTick` `assessment_mode=triage` (a short session that ends with a fixed block, no verdict write), `GuardianTriageResult` (validate, one repair request in JSON mode, sent once more without JSON mode only when the provider rejects it, then fallback; domain check, merged inputs, writes `Guardian.Triage`), operator-owned `GuardianTriageApply` (the only triage step that changes the issue's own fields: `severity` and `phase` through one `core-update-issue` call, behind guards; it never lowers severity for a result that says `escalate`; the focused sessions of the sub-playbooks also write the verdict fields, a case note and a memory row), list `guardian_triage_types` and skill `cortex_triage`; `GuardianTriageApply` and `GuardianTriageResult` are on the denylist | an issue is rated and routed by fixed conditions instead of free-form model prose; the XSOAR 6 edition has the same flow with its own taxonomy |
| Triage playbooks | `GuardianTriageIncident` (same order) and six sub-playbooks plus `GuardianTriageOther`; the deterministic lookups are XSOAR's generic `ip`/`domain`/`url`/`file`/`endpoint`/`cve` commands, `GetUserData`/`GetEndpointData` (skipped when not installed) and a narrow `SearchIncidentsV2`, appended with `GuardianIncidentEvidence mode=append` | `GuardianTriageIssue` (kill switch, Job guard, route, model profile, evidence, triage session, `GuardianTriageResult`, second kill switch check, `GuardianTriageApply`, then a condition on `Guardian.Triage.branch`) and ten sub-playbooks `GuardianTriage<Type>` (`IdentityThreat`, `CloudChange`, `EndpointThreat`, `DataExposure`, `Misconfiguration`, `Vulnerability`, `CodeRisk`, `ExcessivePrivilege`, `AttackPath`, `Other`): guarded read-only lookups, `GuardianIssueEvidence mode=append` (adds them to the pinned packet), one focused model session; `Other` writes a note and has no model. Supporting changes: `GuardianXQL` takes `context_key` (leaves a result at `Guardian.Enrich.<Name>` so two queries in one playbook do not merge) and ships template `resource_access_activity`; the prompt tail says triage mode replaces the verdict block, the case note and the memory row | the typed branches need data the issue does not carry and a model session shaped for the type; the rating and the branch are fixed rules, not prose. Upload the sub-playbooks before the parent. The XSOAR 6 edition has its own six sub-playbooks |
| Evidence packet | `GuardianIncidentEvidence` pre-fetches the incident's fields, linked indicators with reputation (`findIndicators`), open and closed incidents with the same name (`SearchIncidentsV2`) and memory; only scored indicators and earlier closed incidents corroborate | `GuardianIssueEvidence` pre-fetches status, remediation, asset, case, earlier resolutions of the rule and memory (read-only, no compute units, audited) and the tick pins it at the start of the run; it counts as corroboration only for independent reads | the model spent its turns rediscovering what the platform already holds |
| Assessment | one four-label verdict for everything | threat detections keep Malicious / Suspicious / Benign / Inconclusive; posture findings get Confirmed / Not reproducible / Accepted risk candidate with a P1-P4 priority, exposure, owner and fix (`guardian_tick_validate_posture`; the verdict field has three more options) | a configuration finding is a fact to confirm, not a claim to corroborate |
| Verdict gate | reads of the incident count as evidence only by name | `core-get-issues`, `core-get-cases`, `core-get-case-extra-data` and `core-get-issue-recommendations` do not corroborate; the tier-0 command set and the narrowing lifted by a pre-fetched packet include the Cortex readers (the tier-0 set is in this edition only) | reading the issue back through its own API is not corroboration |
| XQL | not available | `GuardianXQL` templates over `guardian_xql_templates`, or any raw query with `query=`, polled until the rows arrive (a script call to `xdr-xql-generic-query` returns PENDING and never the rows); the raw `xdr-xql-generic-query` stays allowlisted, with the free `xdr-xql-get-query-results` to fetch a PENDING one; the tick records each query's `query_cost` and shows the run total; optional caps `xql_max_queries_per_run` and `xql_daily_share_pct` are unset by default | telemetry answers the "who changed it, what else did it do" questions; cost is visible, not limited |
| XQL skill | none (XSOAR 6 has no XQL) | skill `cortex_xql` (list `guardian_skill_cortex_xql`, indexed in `guardian_skills_index`, `foundation`): template first, how to pass values (`DOMAIN\user` with one backslash in a template parameter, `\\` in a raw literal), the datasets and fields verified to exist, the cost rules, how to read zero rows; the prompt tail points to it before a raw query. `GuardianXQL` also reads a doubled `DOMAIN\\user` identity as the same single-backslash account (every other backslash, quote or pipe is still refused) | the model wrote its own XQL with an escaped account the script refused, guessed fields, and queried `dataset = issues` (0.17 compute units against about 0.001 for a filtered `cloud_audit_logs` query on a daily limit of a few units). A separate XSOAR skill may follow |
| Memory capture | `GuardianCaseCapture` from a Job, and `GuardianRunCapture` after each triage focused session (`run:<incident id>`, no digest marker) | `GuardianRunCapture`, a playbook task after the model session, stores `run:<issue id>` (and a per-rule daily digest marker), no Job needed | Jobs are unavailable on some tenants |
| Run modes | per issue | adds `mode=digest` (one report per rule per day) | thousands of posture issues an hour share a few rules |
| `!guardian-tools` | allowlist hits and misses | adds "On this tenant but not allowlisted": commands installed here that Guardian may not use, per brand, with a read/write hint | an operator could not see what Guardian was missing |

| Dashboard and widgets | installed | in the pack, but Cortex platform does not install them | platform; the pack instead ships `XSIAMDashboards/dashboard-GuardianPerformance.json`, a native dashboard of XQL widgets over the `issues` dataset (generated by `scripts/gen_xsiam_dashboard.py`) |
| `GuardianSimulateIncidents` | plain script | its yml carries `skipprepare: [script-name-incident-to-alert]` | for this marketplace demisto-sdk splits an "incident"-named script into the real code (renamed `GuardianSimulateAlerts`) and a deprecated wrapper; an item upload delivered only the wrapper (`Unsupported Command : GuardianSimulateAlerts`). The only script here with "incident" in its name |

## Checked on a live XSIAM 8.15 tenant
- `ScheduledCommand` re-entry works inside a playbook task (tick to tick in about 20 s). Outside a playbook, a bare War Room
  command re-runs only about every 75-120 s and its chain dies at the first timeout; always run the loop through its playbook.
- `|||setAlert` is not needed: the REST read-modify-write used by `guardian_set_incident_fields` (`/incidents/search` then
  `/incident`) updates an existing issue, and `setIncident` also exists as a command.
- `POST /incident` and `createNewIncident` do not create an issue. An issue is created by inserting an alert
  (`POST /public_api/v1/alerts/insert_parsed_alerts`, verified with a Standard key); Guardian's own Job runs have no issue.
- `deleteList` does not exist; lists use `createList`, `setList`, `getList`, `addToList`.
- `demisto-api-*` and `core-api-*` both exist; both are denied to the agent.
