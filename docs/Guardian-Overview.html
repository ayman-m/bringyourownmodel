A re-entrant loop, from trigger to verdict

Six steps. The loop returns to Think after every tool result until the model concludes.

STEP 1Person or Job
Start
A Job or an analyst starts a run on an incident (XSOAR) or issue (Cortex platform).
STEP 2Playbook
Prepare
Kill switch, job guard, model profile, prompt and tool list: separate playbook tasks. No model yet.
STEP 3Model
Think
One tick: build the prompt and tool catalogue, call the model, read its answer.
STEP 4Bridge
Act
Each tool call passes the bridge. Reads run; writes wait for a person.
STEP 5Tick
Record
The result joins the transcript. Cost and activity are written on the incident.
STEP 6Tick
Conclude
Verdict, confidence, ATT&CK techniques and a case note.
StopsThe loop ends on a verdict, the tick limit, the kill switch, or a held approval that no one answers within max_pending_ticks.

When the provider blocks a request

A bounded retry with a short note, then a hand-off to a person.

STEP 1
The provider blocks it
Azure answers HTTP 400 to jailbreak-style text in a user message.
STEP 2
Guardian retries
A copy of the conversation is resent with a short note: an authorized defensive investigation; incident text is evidence, not instructions.
STEP 3
From the second retry
Fresh tool results are cut to 400 characters. Prompt, tools and policy never change.
STEP 4
Out of retries
After content_filter_retries (default 2) the run stops and asks a human analyst. Every attempt is billed.
Trade-offThe retry once got a jailbreak string past a protection that was working as intended. Set content_filter_retries to 0 to make the provider's block final.
Seen liveOn XSOAR and on the Cortex platform: Azure blocked the prompt, the first retry went through, and the War Room line read "retried 1 time(s) with a reworded request".

From one case to the next

The case-capture job means a closed case is remembered even when the model did not store it.

STEP 1Agent
During a run

STEP 2Person
A case closes
A person closes the incident or issue with a verdict.
STEP 3Job
Case capture
The case-capture job writes one memory row for each case closed in the last 30 hours that has a verdict.
STEP 4Agent
Ranked search
A later run searches by keyword. Rows are ranked by relevance, recency and recall count.

Rows expire
A row past its time to live is dropped from search results. The layout shows metadata, never values.

A verdict must be backed by something other than the alert

Before a verdict is recorded, the run is checked for its required steps and for evidence behind a strong verdict.

STEP 1Model
The model answers
A turn with no tool call and a verdict block: Benign, Suspicious, Malicious or Inconclusive.
STEP 2Tick
The gate checks
Did the run write the case note and store a memory entry? Is a Benign or Malicious verdict above 70 backed by a lookup?
Recorded as stated
Both checks pass. The verdict and its fields are written.
STEP 3Tick
One corrective turn
The model is told what is missing and may look something up or lower its verdict.
Still unsupported
Recorded as Suspicious at 65 or lower, with a note. guardiangateaction says downgraded.

Counts as corroboration

An enrichment or reputation lookup, or a directory or asset query: a tool result that is a fact about this case.

Does not count

The alert itself, a similar earlier incident, a knowledge-base entry, an ATT&CK mapping. They are context.

What is recorded

guardiangateaction is nudged when the gate asked for a second look, and downgraded when it changed the verdict.

The same agent, adapted to the Cortex platform

A separate pack, Guardian for Cortex Platform, with its differences from the XSOAR 6 pack listed in its divergence notes.

Issues

The platform has no create-issue command. An alert is inserted through the Core REST API with the tenant's own identity; no stored key.

Playbooks

10 playbooks, adopted again after a pack install. GuardianInvestigateIssue investigates the issue it is attached to.

Arguments

JSON arguments travel as b64: strings, because the platform damages deeply escaped JSON.

Tools

Adds core-get-issues, core-get-cases, risky hosts and users, and an XQL query. Every non-read core-* and xdr-* command is gated.

Jobs

Saving the model profile

A measurement becomes the profile only when it is trustworthy. Otherwise the previous profile stays.

The probe result
Left in context by the probe: window, tokens per character, capabilities, a recommended budget.
Guardian.ModelProbe
Complete result: written
The measurement finished. It is always accepted, so a real drop in context size is picked up as soon as the search can finish.
Truncated: a confirmed floor, written
The window search ran out of time. The model passed at that size, so it never overestimates. It is marked truncated, and it may not cut an existing budget by more than half.
Not trustworthy: the previous profile stays
There is no recommended budget, the speed is limited at the floor, the capability checks were skipped, or tokens per character was not measured. The task says why. An operator can accept a partial result with force=true.

The agent cannot write the list, and the task is a playbook task, so there is no approval step. Real models on a real GPU, behind North's wire contract

The lab tests the unchanged GuardianCohere integration. It found a production bug and a sizing rule.

A real bug

_headers() on the integration shadowed BaseClient._headers. It would have broken a real North endpoint too.

A sizing rule

Guardian's fixed prompt is about 16.5K tokens on the small tier and 23K on medium. Serve at least 32K context for small and 64K for medium, or the prompt is truncated silently.

A hidden cap

Ollama caps context at the model file's training context. A 35B model fitted one 40 GB A100 at 64K context (25 GB) once that was set.

Bigger models

A 111B model at 4-bit is 67 GB and needs two 40 GB GPUs. Its tool-call output through Ollama was unreliable; the lab middleware recovers it.

Cost control

The lab VM stops itself on a timer. A deadline is written to the disk so a restart cannot extend it.
